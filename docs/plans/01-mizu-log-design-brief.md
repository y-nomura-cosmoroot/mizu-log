# mizu-log デザインブリーフ

このドキュメントは、mizu-log（入院患者向けの飲水量・尿量・バイタル記録アプリ）のUIデザインを検討するための入力資料。**別のClaude会話にこのファイルの内容をそのまま渡し、UIモックアップ/ワイヤーフレームの検討を依頼することを想定している。**

前提となる要件定義は [01-mizu-log-requirements.md](01-mizu-log-requirements.md) を参照（本ドキュメントは要件のうち、デザイン検討に必要な部分を抜粋・整理したもの）。

**方針**: このドキュメントはレイアウト・配色・フォント・ワイヤーフレームなど「デザインの答え」を一切決めない。デザインを検討する側が判断できるように、目的・ユーザー像・各画面が扱う必要のある情報・優先順位・操作フロー・制約だけを渡す。

## アプリの目的・背景

入院患者が紙の記録表で行っている「飲水量・尿量・体温・血圧・脈拍・体重・便・食事・内服」の記録をアプリ化する。最大の課題は、紙では1時間枠内に複数回の飲水・排尿があると都度書き換えや自算が必要になること。アプリでは1時間枠内の複数回入力を自動的に合計する。トーンは入院記録の重さ・悲壮感を出さず、ポップで明るい方向性にしたい（具体的な表現方法はデザイン側の判断に委ねる）。

## ユーザー像

- **患者本人**: 記録する人。スマホで操作する。ITに強くない前提。
- **看護師**: 記録を確認する人。患者と同じ端末の画面を一緒に見る。専用の操作UIは不要（閲覧できれば十分）。

## デザインで解決すべき課題（要求される体験。解決方法は指定しない）

- 飲水量・尿量は記録頻度が最も高い項目であり、他の項目より優先して扱われる必要がある。
- 1時間枠内に複数回入力があっても、都度の書き換えや計算をユーザーにさせない（アプリ側で自動合計する）。
- 非IT層（患者・看護師）が迷わず操作できる必要がある。
- 記録は今の時刻・日付が基本だが、過去の時刻・過去の日付を選んで記録するケースがある（例:「4時に飲んだ分を5時に記録する」「昨日の記録を今日つける」）。
- 内服は「その日飲むべきタイミング（例: 朝・昼・晩）」が揃っていない場合に気づける必要がある（脅すような表現は避けたいが、見落としを防ぐ必要はある）。

## 各画面が扱う情報（表示・操作する必要がある内容。レイアウトは指定しない）

### トップ（ダッシュボード）
- 現在見ている記録日の範囲（14:00〜翌13:00台）、前後の日付への移動、日付を選んで移動する手段
- 内服の未チェック状況（未チェックのタイミングがある場合の気づき）
- 飲水量: 本日合計、3つの小計（14-21時台/22-翌5時台/翌6-13時台）、よく使う量のクイック入力、自由入力、個別履歴を見る手段
- 尿量: 飲水量と同じ情報構造
- バイタル（体温・血圧・脈拍・体重）への入力手段、最新値
- 便・食事があったことを記録する手段
- 内服チェックの進捗（例: 3タイミング中いくつ完了しているか）と内服画面への導線

### 飲水量・尿量の個別履歴
- 時間帯ごとにグルーピングされた個別ログ一覧、各ログの編集・削除

### バイタル入力
- 体温・血圧・脈拍・体重それぞれの数値入力、直近の値の一覧

### 内服チェックリスト
- 本日のタイミングごとのチェック状態、そのタイミングで飲む薬名・用量の表示

### 内服マスター編集
- タイミングの追加・削除・並び替え
- 薬の追加・編集・削除（薬名・用量・紐づくタイミングの選択）

### 過去日付の記録閲覧・追記
- 日付を選ぶ手段、選択後は通常のダッシュボードと同じ情報をその日付で表示

### 時刻・日付選択（共通で使う操作）
- 「今」をそのまま使う／時刻を指定する／日付を指定する、の3パターンを切り替えられる

## 主要なユーザーフロー（操作の順序・画面遷移。見た目は指定しない）

1. 患者が水を飲む → 飲水量を記録する操作を行う → 即座に合計に反映される
2. 違う時刻に飲んだ分を後から記録したい → 時刻を指定して記録する
3. 排尿があった → 尿量について同様の操作
4. 看護師は同じ端末の画面を一緒に確認する（専用の確認操作はない）
5. 内服の時間になったら、内服チェック画面で該当タイミングをチェックする。未チェックのタイミングがあればトップ画面で気づける
6. 前日分の記録漏れがあった → 過去日付を選んで、その日のダッシュボードに追記する

## 制約・前提

- 主にスマートフォンでの利用を想定する（画面サイズ・タップ操作前提）。
- 患者・看護師ともにITに強くない前提で設計する。
- データはブラウザ内に保存し、サーバー・DBは持たない（デザイン検討には直接関係しないが、オフライン時の挙動やデータ消失リスクの見せ方を検討する際の前提情報として共有する）。
